# AI Budget Waiting Stroll Goal

`AiBudgetWaitingStrollGoal` is a priority-nine visual fallback for a Player NPC that was recently denied a routine AI worker turn. It must not become another expensive job.

The class name is historical: the “budget” is the CPU resource-sharing scheduler, not RAM or a memory percentage. A denied NPC owns no scheduler resource. An active worker waiting briefly for the separately shared search/path slice still owns its worker resource and must remain inside its real goal rather than starting this stroll.

- It is registered outside `StartupWorkGatedGoal`; otherwise a non-worker could never enter it.
- It extends `WaterAvoidingRandomStrollGoal`, so destination choice uses Minecraft's normal land-biased random-position logic instead of a custom same-Y two-block step. The inherited search uses the usual 10-block horizontal/seven-block vertical range on land and attempts a 15/seven land escape while in water.
- It deliberately retains inherited `RandomStrollGoal.canUse()` cadence and the vanilla no-action-time suppression. Do not call `trigger()` from the wrapper or replace that policy with an unconditional 80-160 tick timer: remote force-loaded non-workers otherwise keep starting optional paths indefinitely.
- A successful vanilla target selection still needs a separate server-wide waiting-stroll path-start admission. This admission runs after vanilla selects a destination, permits at most one optional navigation-path creation per server tick, and never grants a routine worker or expensive job slice. It prevents denied visual paths from batching while leaving vanilla's already-throttled position selection and real job arbitration unchanged.
- A successful activation creates at most one navigation path. That synchronous probe uses `PathNavigationAi.createBoundedPath(..., 0.15F)`, which restores the navigator's normal visited-node multiplier in `finally`. A non-empty bounded best-effort path is allowed even if the cutoff prevented exact arrival, matching vanilla stroll's useful partial movement; an empty/failed probe stops stale navigation rather than inheriting movement from an old job.
- Waiting stroll is optional visual work. Once the stable rolling server tick reaches 50 ms, both activation and continuation yield until normal 20-TPS headroom returns. Target selection and path creation contribute to the monitor's `waitingStrollMs` timing so a live warning can distinguish this helper from other idle entity work.
- It keeps the vanilla `MOVE` flag at priority nine. It yields immediately when a target, healing/upward escape, a routine worker turn, or any higher-priority conflicting goal becomes available. Water is allowed only so the inherited water-avoiding logic can select a land escape; an airborne NPC outside water is not eligible.
- Scheduler denial, land/water eligibility, and grounded state are activation conditions, not continuation conditions. Once admitted under healthy server load, the inherited navigation may complete its normal route even after the short denial marker expires and while the mob jumps over terrain. A newly available higher-priority MOVE goal still preempts priority nine normally; there is no routine-resource bypass.
- The goal retains the exact path installed by `start()` and continuation requires that the live navigation still owns that path (or its destination). `RandomStrollGoal.stop()` already stops navigation when optional work yields; the ownership check instead prevents a failed activation from continuing on a stale route. Every early `start()` exit stops navigation, including a destination in an unloaded chunk, so `super.canContinueToUse()` cannot mistake an older job/combat path for a successful stroll.
- Do not require the entire vanilla random-position search radius to be loaded. Activation is already skipped before target selection when stable MSPT is at least 50, the selected destination must be loaded before the bounded path probe, and broad neighborhood checks would suppress legitimate routes near a loaded boundary without preventing the measured overload samples. Retained `waiting ... stroll` detail may outlive the goal briefly; use `runningGoals`, navigation ownership, and `waitingStrollMs` rather than the detail string alone for attribution.
- Its trace detail explains that the NPC is strolling while waiting for an AI worker turn. It does not claim that prerequisite-blocked NPCs have budget starvation unless the scheduler actually recorded a denial.
